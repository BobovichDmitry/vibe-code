## Вопрос 1 — e2e-стиль при переносе механики задач (задача 01)

В референсе `agent-hosted` e2e — **API-based** (изолированный backend на порту 3511 + mock-ai на 9101, хелперы, сценарии mock-ai/mock-mcp). Скилл `e2e-writer` и стадия `test-runner` в `task-batch-solver` завязаны на этот стиль.

В текущем проекте e2e — **браузерные через CDP** (`e2e/fixtures.ts` → `connectedBrowser`/`connectedPage`, реальный Chrome на `--remote-debugging-port=9222`, `@playwright/test` напрямую).

**Вопрос:** как поступить с `e2e-writer` и e2e-стадией `task-batch-solver`?
- **(a)** Адаптировать `e2e-writer` под браузерно-CDP стиль (писать Playwright-спеки через `connectedPage`, как в существующих `e2e/tests/*.spec.ts`), а `test-runner`/`test-fixer` запускать через существующий `npm run test:e2e` (нужен запущенный Chrome CDP + dev-серверы — пользователь поднимает).
- **(b)** Перенести `e2e-writer` как есть (API-based), и параллельно заложить отдельную задачу на перевод e2e проекта на API-based стиль с изолированным backend + mock-ами (как в референсе).
- **(c)** Сделать `e2e-writer` опциональным/заглушкой сейчас, а `task-batch-solver` — без обязательной e2e-стадии (только code-solver → docs-maintainer → commit), до отдельного решения по e2e.

Моя рекомендация: **(a)** — меньше вторжений, сохраняет текущий e2e-движок. Но (b) даст более быстрые/стабильные тесты в долгосрочной перспективе (как у референса).

Ответ: пусть пишет как сейчас с запуском браузера, но чтобы также он умел запускать тесты через api стиль. Важно, чтобы можно было через env управлять браузером и запускать его headless при необходимости

## Вопрос 2 — брендинг в каркасе без settings-модуля (задача 04)

Референс `agent-hosted` берёт название продукта/favicon из `GET /api/settings/branding` (публичный эндпоинт модуля `settings`). В нашем каркасе модуль `settings` удаляется (задача 02 — это telegram-настройки, не нужные голому каркасу).

**Вопрос:** откуда `useBranding` берёт `title`/`faviconUrl`?
- **(a)** Зашить константами в `useBranding.ts` (`'VibeSetup UI'`, `/favicon.svg`) + `apply()` к DOM, без сетевого запроса. При появлении у пользователя своего settings-модуля — заменить на `GET /api/branding`. Коммент-заглушка в коде.
- **(b)** Добавить минимальный публичный эндпоинт `GET /api/branding` (без отдельного модуля — просто контроллер с константами из env `BRAND_TITLE`/`BRAND_FAVICON_URL`), чтобы бренд настраивался через env без БД.
- **(c)** Оставить только `useBranding`-скелет с константами, эндпоинт не добавлять (минимальный каркас).

Моя рекомендация: **(b)** — даёт env-настраиваемый бренд без бизнес-модуля, близко к референсу и удобно для ansible (задаёт `BRAND_TITLE` в env). Но (a) — самый минималистичный.

Да, давай так как ты предлагаешь.

## Вопрос 3 — HTTPS: nginx-proxy vs одиночный nginx+certbot (задача 05)

В референсе `docker-compose.nginx-proxy.yml` использует **nginx-proxy** + Let's Encrypt (мультитенант: один proxy на много контейнеров-клиентов). В нашей постановке — **один сервер, один домен, одно приложение**.

**Вопрос:** как ставить HTTPS?
- **(a)** Одиночный `nginx` + `certbot` на самом сервере (ставятся ansible), проксируют `:3000`. Проще для одиночного сервера, не требует отдельного docker-контейнера proxy. Так заложено в задачу 05 сейчас.
- **(b)** Оставить паттерн nginx-proxy из референса (контейнер `nginxproxy/nginx-proxy` + `nginxproxy/acme-companion` в docker-compose, домен через `VIRTUAL_HOST`/`LETSENCRYPT_HOST`). Ближе к референсу, но тяжеловатнее для одиночного сервера.
- **(c)** Вообще без HTTPS в ansible-скриптах (только `:3000` наружу), HTTPS настраивает пользователь отдельно/вручную.

Моя рекомендация: **(a)** — одиночный nginx+certbot через ansible, домен из переменной. Но если планируется позже несколько приложений на одном сервере — (b).

Ответ: Идем по варианту B. Чтобы потом, в будущем ,можно было было держать несколько проектов на базе этого сетапа.

## Вопрос 4 — docker-compose: prod-вариант и проброс портов (задача 05)

Сейчас `docker/docker-compose.yml` пробрасывает `5432` postgres наружу (для dev-удобства). На проде postgres лучше держать внутри compose-сети, наружу только `:3000` (или только через nginx).

**Вопрос:** как организовать compose для prod?
- **(a)** Создать отдельный `docker-compose.prod.yml`: app + postgres, `5432` НЕ пробрасывается наружу, наружу только `:3000` (nginx проксирует). Ansible использует именно его.
- **(b)** Один `docker-compose.yml`, но prod-env убирает проброс `5432` через override-файл `docker-compose.prod.override.yml`.
- **(c)** Оставить один `docker-compose.yml` как есть (с пробросом `5432`), ansible использует его; проброс `5432` на проде — риск, но просто.

Моя рекомендация: **(a)** — отдельный prod-compose без проброса БД наружу, чистый prod-профиль.

Ответ: Идем по пути А.

## Вопрос 7 — архив исходников для sftp (задача 05)

Ansible распаковывает архив на сервере. Какой формат/состав архива ожидается?

- **(a)** `tar.gz` всего проекта, собранный на ПК командой вида `tar --exclude=node_modules --exclude=dist --exclude=logs --exclude=data --exclude=.git -czf vibesetup.tar.gz .` — ansible распаковывает в `/opt/vibesetup` и там собирает (`docker compose build`). В archivе — исходники, **сборка идёт на сервере** внутри Docker.
- **(b)** Архив с уже собранным `dist/` (frontend+backend build на ПК) — ansible только копирует и `docker compose up`. Быстрее деплой, но требует той же Node-версии на ПК.
- **(c)** Готовый Docker-образ пушится в registry, ansible только `docker compose pull && up` (архив исходников не нужен). Это другой workflow, не «sftp архива».

**Вопрос:** пользователь сказал «sftp передаёт архив с исходниками» — это (a)? Или (b)? Registry (c) вроде исключён формулировкой.

Моя рекомендация: **(a)** — исходники в архиве, сборка в Docker на сервере (соответствует «архив с исходниками» и multi-stage Dockerfile).

Ответ: твой вариант ок. Делаем А.

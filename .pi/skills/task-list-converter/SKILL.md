# Task List Converter

Превращает «голый» список коротких формулировок (обычно markdown-буллеты или просто строки в одном файле) в **полноценные файлы задач** очереди `tasks/`, готовые к разбору скиллами `task-solver` / `task-batch-solver` или ручной реализации.

## Главная ценность

Скилл **НЕ просто разбивает текст на файлы-заголовки**. Для каждой задачи он:

1. **Анализирует код проекта** (`rg`/`read`) — находит затронутые файлы, эндпоинты, компоненты, существующие паттерны.
2. **Оценивает готовность**: однозначно ли понятно решение и есть ли вся инфраструктура для него.
3. **Фиксирует анализ прямо в файле задачи** — контекст, критерии приёмки, подсказки по реализации, способ проверки. После этого задачу можно взять и реализовать за один проход без повторного исследования.

## Когда использовать

Триггеры (скилл подгружается по описанию автоматически):

- «конвертируй список в задачи» / «разбей файл с задачами на отдельные»
- «создай задачи из списка» / «из `small_tasks.md`»
- «преврати строки файла в задачи очереди»
- «оформи список как задачи `tasks/`»

Или явный вызов: `/skill:task-list-converter`.

## Вход

- **Источник** — путь к файлу со списком. Явно (`конвертируй tasks/small_tasks.md`) или угаданный: если пользователь не дал путь, ищи в `tasks/` вероятный кандидат (имя вида `small_tasks.md`, `list.md`, `raw_tasks.md`, `backlog.md`, `ideas.md` — НЕ `index.md` и НЕ файлы из `todo/`/`done/`). Если кандидатов несколько/нет — **спроси** путь, не угадывай вслепую.
- **Формат источника** — любой: markdown-буллеты (`-`/`*`), нумерованный список, просто строки. Пустые строки и комментарии (`<!-- -->`) игнорируй. Каждая непустая осмысленная строка/пункт = одна задача.
- Длинную строку с несколькими задачами в одной не дроби — бери как есть; если явно видно «и/или», «;» с разными темами — уточни у пользователя.

## Алгоритм

### 0. Загрузи контекст очереди
1. Прочитай **файл-источник** (список).
2. Прочитай `tasks/agents.md` (правила работы с `tasks/`) и `tasks/index.md` (текущее состояние — чтобы не плодить дубликаты и корректно вписать новые пункты).
3. Подгляди формат у пары готовых файлов из `tasks/done/` (если есть) — держи стиль проекта.

### 1. Для каждой строки-задачи

#### 1.1. Сформулируй slug
- Короткий, английский, `snake_case`, отражает суть (не транслит русского).
- Примеры: `rename_user`, `add_reminder_pagination`, `fix_login_redirect`, `users_table_sort`.
- Если формулировка задачи уже содержит подходящее ключевое слово — бери его.

#### 1.2. Проверь дубликат
- По slug ИЛИ по смыслу в существующих `tasks/index.md` (Todo/NeedInfo/Done) и в `tasks/todo/`, `tasks/done/`.
- Если задача уже есть (или близкий дубликат) — **не создавай новый файл**. Сообщи пользователю: «Задача „X" уже есть как `<slug>` (в Todo/Done) — пропускаю». Можно предложить дополнить существующий файл, но не перезаписывать молча.

#### 1.3. Проанализируй суть и изучи код
- Пойми, что пользователь хочет (часто формулировка разговорная — переформулируй в техническую).
- Найди затронутые файлы через `rg`/`read`: эндпоинты (`apps/backend/src/**`), компоненты/views/composables (`apps/frontend/src/**`), сущности/миграции.
- Определи, **что уже есть** (готовые эндпоинты, методы, паттерны — их переиспользуем) и **чего не хватает** (новый UI, новый метод, правка условия).
- Ищи аналогичные паттерны в проекте (напр. лоадер в `RemindersView` → reused в `ManageUsersView`).

#### 1.4. Оцени готовность → ветка TODO или NEEDINFO

**TODO** (однозначно понятно + всё есть) — выполнены ВСЕ условия:
- Понятно, какие именно файлы затронуть.
- Backend-эндпоинт/метод либо уже есть, либо тривиально добавляется по существующей конвенции.
- Фронт-метод/composable либо уже есть (переиспользуем), либо пишется по готовому паттерну из проекта.
- Нет нужды во внешних данных (макет, ключи, доступы, референс) или архитектурном решении пользователя.
- Нет жёсткой зависимости от другой невыполненной задачи.

→ Создавай файл в **`tasks/todo/<slug>.md`** по шаблону TODO (ниже), пункт в `index.md` → `## Todo`.

**NEEDINFO** (неоднозначно или нехватка данных) — любое из:
- Несколько равнозначных трактовок, меняющих результат (что именно считать/где разместить/какой формат/поведение в edge-case).
- Нужны внешние данные: макет, ключ, доступ, ссылка на референс, прод-значение, поведение третьей стороны.
- Требуется архитектурное решение пользователя (напр. новое хранилище, новая сущность, выбор стратегии).
- Жёсткая зависимость от другой невыполненной задачи или от ответа пользователя.

→ Создавай файл в **`tasks/todo/<slug>.md`** по шаблону NEEDINFO (вопросы внутри), пункт в `index.md` → `## NeedInfo` (файл остаётся в `todo/` — это канон проекта, см. `tasks/agents.md`).

> Важно: «я не уверен» — это НЕ повод уходить в NEEDINFO без попытки. Сначала изучи код: часто «непонятно» рассасывается после `rg`. NEEDINFO — для подлинной неоднозначности/нехватки, а не для лени.

### 2. Шаблоны файлов задач

#### Шаблон TODO (задача готова к реализации)

```md
<исходная формулировка задачи (можно слегка причесать, но без потери смысла)>

---

## Контекст (анализ кода)

- <что нашёл в коде: какие эндпоинты/методы/компоненты уже есть, что переиспользуем, чего не хватает>
- <ссылки на конкретные файлы: `apps/.../X.vue`, `apps/.../Y.ts`>
- <существующие паттерны проекта, которые применимы>

## Acceptance criteria

- <конкретное, проверяемое условие>
- <...>
- <edge-cases: пустой ввод, гонки и т.п.>

## Подсказки по реализации

- Все правки — <только фронт / фронт+бэк / ...> (файлы: ...).
- <что переиспользовать: метод X уже импортирован, composable Y, паттерн из Z>
- <на что обратить внимание>

## Проверка

- `npx vue-tsc --noEmit` в `apps/frontend` и/или `npx tsc --noEmit` в `apps/backend` — без ошибок. dev-серверы и e2e не запускать (по правилам проекта).
```

#### Шаблон NEEDINFO (вопросы пользователю)

```md
<исходная формулировка задачи>

---

## Контекст (анализ кода)

- <что удалось понять из кода; что осталось неясным>

## Вопросы (NeedInfo, YYYY-MM-DD)

1. <конкретный вопрос с контекстом и вариантами ответа>
2. <...>
```

Файл **остаётся** в `todo/`; в `index.md` пункт идёт в `## NeedInfo` со ссылкой `todo/<slug>.md`.

### 3. Обнови `tasks/index.md`

Канонический формат (см. `tasks/index.md` + `tasks/agents.md`):

```md
## Todo
1. [slug.md](todo/slug.md) — краткое описание (в скобках — ключевой механизм)

## NeedInfo
<!-- задачи, ожидающие ответа. Вопросы — внутри файла -->

## Errors
<!-- технически неудавшиеся -->

## Done
<!-- выполненные -->
```

- Вписывай новые задачи в `## Todo` / `## NeedInfo` **нумерованным списком**, сохраняя порядок источника (первая строка источника → первый пункт).
- Описание в index — **краткое** (одно предложение), но информативное: не копия исходной разговорной формулировки, а техническая суть + в скобках ключевой механизм/решение. Пример:
  > `fix_login_redirect.md` — починить редирект после логина (hash-router `/#/admin`, JwtAuthGuard на `/api/users`)
- Перенумеруй список после вставки.
- Не трогай существующие пункты (кроме перенумерации).

## Slug-конвенция (кратко)

- `snake_case`, английский, ~2–4 слова.
- Отражает **действие/суть**, не дословный перевод.
- Уникален в рамках `tasks/` (проверяй по `todo/`, `done/`, `index.md`).

## Дедупликация и дрейф

- Дубликат по смыслу → пропуск + сообщение пользователю (не перезаписывай).
- Если источник ссылается на задачу, которая **уже выполнена** (есть в `## Done`) — сообщи, не создавай заново (можно предложить проверить, не регресс ли).
- Если в `todo/` лежит «свободный» файл, которого нет в `index.md` — не твой случай; не трогай (это забота `task-solver`).

## Ограничения проекта (из корневого AGENTS.md)

- **НЕ запускай dev-серверы** (`dev:backend:log`, `dev:frontend:log`) и **НЕ запускай e2e**. Для проверки типов (если что-то правил) — `tsc --noEmit` / `vue-tsc --noEmit`. Сам скилл обычно код не пишет, только файлы задач — но если поправил что-то попутно, проверь типами.
- **НЕ вызывай `chrome_devtools_*` напрямую** — браузер через сабагента `browser-checker`.
- Пиши на русском (формулировки, контекст, вопросы).
- Соблюдай архитектуру из `AGENTS.md` (API prefix `/api`, TypeORM, Vue 3 + Tailwind SPA, hash-router, конвенции `tasks/`).

## Отчёт пользователю

После обработки всего файла-источника — короткая сводка-таблица:

```markdown
Разобрал `<источник>` (N строк): создано K файлов в `tasks/todo/`.

| # | slug | Задача | Ветка |
|---|------|--------|-------|
| 1 | fix_login | Починить редирект логина | Todo |
| 2 | ... | ... | NeedInfo |

`tasks/index.md` обновлён.
```

Для NeedInfo-задач отдельно перечисли суть открытых вопросов, чтобы пользователь мог ответить сразу.

## Чек-лист одного прогона

- [ ] Прочитал файл-источник + `tasks/agents.md` + `tasks/index.md` (+ глянул стиль в `tasks/done/`).
- [ ] Для каждой строки: slug → проверка дубликата → анализ кода (`rg`/`read`) → оценка готовности.
- [ ] TODO-файлы содержат: Контекст (анализ кода), Acceptance criteria, Подсказки по реализации, Проверку.
- [ ] NEEDINFO-файлы содержат: Контекст + секцию «## Вопросы (NeedInfo, дата)».
- [ ] Все файлы созданы в `tasks/todo/` (NeedInfo-файлы — тоже в `todo/`, в index уходят в раздел `## NeedInfo`).
- [ ] `tasks/index.md` обновлён (нумерация, порядок источника сохранён).
